First, inspect the actual diff:

Then evaluate the change against:
1. Correctness — does the implementation satisfy the issue's acceptance criteria?
2. Build/test — did the verify/test results above pass? A failing check above
   is an automatic FAIL regardless of anything else here.
3. Scope — does the change touch only what the issue requires?
4. Standards — does the code follow the conventions of the surrounding files?
5. No regression — any obvious side effects on existing behavior?
6. Security (run this as part of the same review, not a separate pass):
   - Authorization/authentication — missing or incorrect permission checks;
     IDOR (acting on an id without an ownership/authz check); privilege
     escalation.
   - Secrets — hardcoded keys/tokens/passwords; secrets logged or echoed;
     secrets committed instead of handled via a secret manager.
   - Injection — unparameterized SQL/query building from unvalidated input,
     command injection in shell-outs, path traversal.
   - Input validation / output encoding — unvalidated input reaching a
     database, filesystem, or shell; XSS; SSRF.
   - Data exposure — over-broad API responses, PII in logs or telemetry.
   Classify the worst finding: Critical/High is blocking — treat it as a FAIL
   exactly like a failed acceptance criterion. Medium/Low — note it in your
   feedback but do not block solely on it.
